# アンチパターン禁止ルールの標準手順

出典: Lauren Tan「All Code Is Slop (Except Mine)」（AI Engineer Code Summit）の
「修正は決定的チェックへ変換する」原則。方針の正本は agent-policy の
decisions/2026-11-17-lauren-tan-deterministic-checks.md。

## 原則

エージェントや実装への訂正は、散文ルールへ書き足す前に、次の順序で検討する。

1. 決定的チェック（lint・型・テスト・スキャン）へ変換できないか
2. API 設計・アーキテクチャで、問題のカテゴリごと消滅させられないか
3. それでも残るものだけを散文ルールにする（最小限に保つ）

## 修正が起きたときの標準手順

1. **カテゴリを特定する**: 単発のミスか、同型の再発があり得るパターンかを見分ける。
   再発があり得るものだけをルール化の対象にする。
2. **ルールを追加する**: 新規発生を防ぐチェックを軽い層（static 段階）に入れる。
   既存の仕組みに載せる: ruff のルール選択、型チェック、専用スキャンスクリプト
   （scripts/scan_secrets.py、scripts/scan_justification.py が型）。
3. **既存分を掃除する**: ルールを入れたら、既存コードの同パターンも同時に直す。
   新規だけ止めて既存を残すと、既存分が「確立したパターン」としてコピーされ続ける。
4. **抑止はレビュー対象にする**: 誤検知ややむを得ない例外は、行末の allow コメント
   （例: `justification-scan: allow`）で抑止し、その追加自体をレビューで確認する。

## エラーメッセージの設計指針

チェックのエラーメッセージは、エージェントと人間の双方への「教示」として設計する。

- 何が問題か（検出内容）を具体的に書く
- なぜ問題かを書く（陳腐化する、パターンとしてコピーされる、等）
- 正しい直し方を書く。表層的な回避策の手順は提示しない
  （提示すると、エージェントは根本原因ではなく回避策を選ぶ）
- 抑止方法がある場合は、その手続き（allow コメントとレビュー）まで書く

## 依存方向のチェック

層やディレクトリの境界（例: UI 層から基盤層への直接 import 禁止）は、
散文の規約ではなく、各リポジトリの lint 設定や依存グラフ検査で機械的に守る。
境界を作ったら、同時に検査も入れる。検査のない境界は規約として扱わない。

## 歯止め

- ルール追加の前に「カテゴリごと消せないか」を必ず検討する（原則の2番目）。
  設計で消せるものをルールで塞ぐと、ルールだけが増え続ける。
- 誤検知が続くルールは、範囲を狭めるか廃止する。守られないルールは
  他のルールの信頼も下げる。
- 語彙ベースのスキャン（scan_justification.py 等）の語彙はリポジトリごとに調整する。
  一般的すぎる語（手順を示すだけの語など）は入れない。
